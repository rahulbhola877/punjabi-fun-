## Finding

**IR-01 — S3 / P1: Space flight visibility missed the shadow geometry created later. Resolved in follow-up source; accepted after independent re-review and focused rerun.** Rendered acceptance remains pending.

`SpaceWorld.ts` now correctly batches lunar colour meshes before recording `lunarMeshes`, but calls `showLunar(false)` before `finishDistrict`. `finishDistrict` accepts meshes with numeric `visibility=0` because eligibility checks `isVisible`, then builds an independent `district-static-shadow-depth` mesh. That depth mesh is created after the lunar snapshot, remains enabled with visibility 1, and is explicitly registered as a caster. Its layer mask 0 excludes colour cameras, **not** the explicit shadow render list. Earth launch geometry is assigned `receiveShadows=true`; hidden lunar buildings therefore remain eligible to cast onto the departure set.

The same later setup creates `district-moving-contact-shadows`, outside the snapshot. Its per-frame update does not inspect root enable/visibility state, so hiding the lunar actor bodies does not hide those contact quads. This path predates part of this repair, but restoring batched building silhouettes makes accepting the colour-only flight fix insufficient.

Minimal CPU composition reproduced the state with two real Babylon boxes and actual `batchStatic`, `districtShadowSilhouette` and `batchShadowCasters`: the colour source was hidden, yet a 72-index depth mesh was enabled/visibility 1 and absent from the captured array. This was not a rendered screenshot claim. The graphics owner then repaired the lifecycle; this reviewer changed no production source.

**Follow-up accepted:** `SpacePresentation.ts` batches and captures live lunar colour meshes, hides them initially, and returns a one-time reveal callback. It restores original visibility **before** `finishDistrict` constructs shadow/LOD resources, avoiding an empty cached map. Natural descent and skip both disable departure/flight stars before revealing; later descent frames reuse initialized resources. Calls after scene disposal do nothing. Natural setup failure reaches the existing loop cleanup; click-triggered setup failure now also exits safely. The flight is intentionally monotonic: there is no unsupported hide-again operation after initialization. Final reviewed files: [digests](evidence/INDEPENDENT-lunar-final-sha256.txt).

Deferring the whole `finishDistrict` also defers ACES tone mapping, exposure 1.12/contrast 1.08, reflection assignment, LOD creation and material freezing until descent/skip. Launch/crossing therefore use scene defaults. This is a source-known presentation/workload change, not a demonstrated pixel defect or a request for broader repair; the normal launch/descent visual gate must cover it.

## Accepted source behavior and limits

- **Hero position aliasing:** `player` and `actorBodies` reference each real Babylon root's existing `Vector3`; neither Japan/China nor `KitHuman.sync` replaces these vectors. Strict identity self-exclusion therefore works, and player movement is immediately visible to subsequent walker checks. A separate CPU probe using real `TransformNode` roots confirms reciprocal separation with the shared references. `DistrictControls.follow` only reads the player coordinates. No alias regression found.
- **Foot-level collision:** the scalar XYZ interface matches these root foot positions. Candidate Y follows each district's height plus elevation; swept XZ segments prevent through-body and grazing-chord crossings. Tangent sliding rechecks all actors and scenery; axis fallback also rechecks each actual displacement. Existing overlap permits outward movement without teleporting actors. Current jump height stays below the 1.7 m upright body filter. This remains simple upright footprint collision, not limb collision or a general swept 3D solver.
- **Patrol movement:** production maxima equal authored sine maximum speeds (Japan 0.84 m/s; China river 1 m/s; market 0.56 m/s). Each walker approaches an absolute target, discards blocked travel, waits on its fixed lane and can reverse; it cannot accumulate catch-up teleport distance. `Character.play` returns early for the same current clip, so per-frame idle/walk selection does not restart the animation. The route tests cover 180 seconds at 5 FPS, 30 seconds blocked, static/NPC clearance, recovery and endpoints. No new route or speed defect found. Permanently occupied lanes intentionally remain blocked.
- **China pole clearance:** optional radius preserves the default 0.42 m player footprint. NPC radius 0.36 m plus 0.12 m pole leaves the authored market lane 0.02 m clearance. Boundary tests reject a further 0.03 m approach; this is a causal route fix, not relocation or a looser player collision threshold.
- **Batch state:** grouping now partitions visibility, rendering group, layer mask, shadow reception and caster eligibility in addition to material/cell/orientation. Replacement properties are copied before freezing. Babylon's installed merge code itself preserves side orientation and bakes source transforms; source disposal does not remove the shared material. New tests cover six state partitions, caster versus trim partitioning, transformed vertices/UVs, disabled/dynamic exclusions and parent-baked assets. No regression found for the actual selected static callers. This utility still assumes its explicitly selected assets are immutable and does not preserve arbitrary per-mesh application metadata or independent future toggles.
- **Shadow classification:** shared name/material exclusions and explicit metadata preserve eligible authored buildings under replacement names while keeping trim, roads and submerged geometry out. Restored caster counts may increase initial shadow work; no performance win or pixel-quality acceptance follows from state tests alone.
- **Space colour ownership:** the moved batch call precedes the snapshot; later `showLunar` references the actual live replacements. A CPU probe confirms hidden colour geometry restores its original visibility. That part is accepted independently of IR-01.
