### GP-01: lost Space flight visibility ownership

At entry source, `SpaceWorld.ts:258–260` recorded `lunarMeshes` and set numeric visibility to zero, but `SpaceWorld.ts:381` then called `batchStatic`. That utility filtered `isVisible` but did not preserve numeric `visibility`, and Babylon `Mesh.MergeMeshes` creates a replacement with default visibility 1. The saved array retained disposed originals. Calling `showLunar(false)` could no longer hide the replacement.

The fresh 2.32-second CPU diagnostic used two actual Babylon habitat boxes, the real `batchStatic`, and the same snapshot/hide/merge/show pattern. Both original boxes were disposed, the replacement was enabled with visibility **1**, the saved list did not contain it, and both subsequent show/hide calls left it at **1**. Exit status was 0. Vite emitted dependency-scan shutdown messages after the result because the temporary SSR server was closed; these were harness teardown noise, not a game/browser result.

Repair: [SpacePresentation.ts](../../src/alternate/SpacePresentation.ts), called by [SpaceWorld.ts](../../src/alternate/SpaceWorld.ts), batches before recording lunar visibility. [batchStatic.ts](../../src/alternate/batchStatic.ts) partitions and retains numeric visibility, rendering group, layer mask and shadow reception, in addition to the existing material/cell/side-orientation grouping. The existing independent ownership of story items, actors and the rocket remains in the call-site selection.

The batching regression creates twelve meshes across six distinct render states. Before repair they incorrectly collapsed into one replacement. After repair the six state groups survive. This is meaningful coverage of the lost-state mechanism, but the actual flight owner/order must still receive the normal-browser sequence below.

**Independent follow-up IR-01:** [INDEPENDENT_REVIEW.md](INDEPENDENT_REVIEW.md) correctly rejected color-only ownership as insufficient. `finishDistrict` originally ran while lunar color meshes were hidden and created an independent depth proxy/contact geometry afterward. The proxy was enabled, had visibility 1, and was registered in an explicit shadow list; its color layer mask 0 did not prevent shadow submission. The independent CPU probe confirmed this with 72 depth indices. No visible shadow artifact was claimed from that CPU probe.

The follow-up changes the lifecycle rather than attempting to cache a blank map. The production presentation helper initially hides the live color batches, preserving authored visibility and enabled states. On first reveal it restores those states **before** running actual `finishDistrict` once. Both natural descent and the skip/landing path disable departure/stars first. Lunar depth/contact geometry therefore does not exist during launch/crossing. Repeated reveal calls do not create new resources; abort-before-reveal creates none and callbacks after scene disposal are ignored. Deferred preparation errors from the skip button now take the normal scene-exit cleanup path; the render loop already catches its own preparation errors.

[spacePresentation.test.ts](../../tests/spacePresentation.test.ts) exercises the production helper with real district setup, caster selection, shadow/contact construction, cached-map configuration and disposal. Only GPU cube-texture upload is substituted because NullEngine has no WebGL context; a minimal canvas context supports contact-texture construction. Tests confirm absent resources before reveal, restored color visibility at initialization, 72 depth indices afterward, unchanged resource counts on repeat reveal, preservation of a disabled quest object/faded mesh, and disposal/abort behavior. These are lifecycle tests of the shared reveal path, not actual input/flight-frame acceptance. An eager-initialization extraction of the original sequence failed all three cases (initialization saw hidden visibility 0 rather than restored 1). Two interim test runs exposed fixture-only missing document listeners and unsupported raw-cube upload; both harness defects were corrected. The final focused run passed 4 files / 15 tests.

Full district presentation, including tone mapping/reflection setup, now initializes at descent. The launch look therefore needs explicit current pixel review along with shadow absence and first-descent compilation cost. The independent reviewer accepted the revised production lifecycle and separately reran the three lifecycle tests with one worker: **3/3 passed**. Both the reviewer and this report retain the full-presentation timing implication and the actual browser evidence gap; no claim of fresh visual acceptance follows from these tests.

### GP-02: shadow classification erased by merging

At entry source, `batchStatic.ts:26` renamed replacement meshes `static-batch-*`, and only the parent-baking path set `districtSilhouette`. `DistrictLook.ts:120–126` selected major casters by authored names or that metadata. Neon calls batching over `block*` and `roof*` (`NeonWorld.ts:237`), and Space over `habitat*`/roof pieces. Their renamed default batches could no longer match. Japan's selected `pondEdgeStone` geometry also passes through the default batch call (`JapanWorld.ts:176–182`).

The CPU diagnostic confirmed both `habitat0` and `habitat1` matched the exact original silhouette predicate while their merged replacement did not. New regression geometry combines roofs, blocks, habitats and explicitly marked custom architecture with windows and submerged stones sharing one material. Before repair it collapsed into one group with lost policy; afterward caster and noncaster geometry remain separate, with exactly 48 triangles in each group.

Repair: [DistrictShadowPolicy.ts](../../src/render/DistrictShadowPolicy.ts) centralizes the existing material/name exclusions and silhouette selection. Both batching and [DistrictLook.ts](../../src/render/DistrictLook.ts) use it. Replacement meshes retain an explicit caster role, and batches cannot mix roles. The prior explicit parent-baked source-asset treatment is retained and covered separately. Roads, trim, submerged stones and glow geometry are not blanket-promoted to casters.

**Workload implication:** restoring missing silhouettes and preserving state boundaries can increase color-batch count, initial shadow geometry and initial shadow-map cost. That is restored rendering work, not a performance win. The fixed map remains cached, but its actual first-render and steady-render costs have not been measured on this repair. Do not remove restored shadows to recover historical counts.

## Rendering, material and lifecycle assessment

- **Main and Canada:** Canada is an authored district within the main scene, sharing its materials, fog, dynamic sun, shadow selection, weather and physics. Main opaque scenery is spatially/material batched with frozen matrices. `EnabledMeshCandidates` tracks effective parent enablement and restores the original scene callback on disposal. This existing optimization should survive new meshes, parent toggles and removal.
- **Main shadows:** `World.ts:160–186` uses 2048/4096 maps. `followShadows` selects scenery when the anchor moves 12 m and dynamic casters about four times per second, updates the render list only when membership differs, and uses nearby depth cells. `StaticShadowCells` preserves alpha-cutout fallback and releases distant proxy buffers. Keep shadow-only proxies out of color candidates and distinguish actual allocated buffers from `Scene.getTotalVertices()` candidate counts.
- **District materials/shadows:** `DistrictLook.ts` shares generated maps by finish, keeps skin vertex color/skin attributes, removes generic relief from smooth plaster/terrain and restricts reflections to polished surfaces. Fixed casters use one cached shadow map; moving actors use approximate batched contact silhouettes, not live wall/limb shadows. Ground contacts sample terrain height, so roof/jump/rover grounding warrants pixel inspection. Shadow-off returns before the material-freeze loop; any cost investigation there must compare equivalent shading and startup/steady work, not assume freezing is always safe.
- **Water:** main canal and alternate clear water inject one surface shader pass rather than rendering whole-scene reflections. Clear water is transparent and two-sided; overlap/sorting, shore contact and low-angle glints still need pixels. Observer cleanup is material-owned in `CanalWater.ts:15–20` and `ClearWater.ts:22–29`. `WaterContactEffects` preallocates eight disabled rings and reuses them. A higher water cost cannot be inferred merely from its appearance; measure screen coverage and actual submissions first.
- **World transitions:** `Game.ts:3031–3056` loads alternate modules before stopping the main loop, pauses audio/input and stops that specific loop at `:3060–3067`, then restores it and resets the clock in `finally` at `:3123–3129`. The four 3D worlds stop their own loops, abort listeners, dispose controls/people/scene/overlay, and clean up setup/render errors. Pixel cancels its own RAF and aborts listeners on normal exit. No new leak was demonstrated; normal-return historical checks do not prove every failure path. The main scene intentionally remains allocated during alternate visits.
- **Same-map Canada/airfield travel:** `arriveAt` synchronizes camera visibility and shadow selection; readiness waits for local enabled scenery and has an eight-second timeout with origin recovery (`Game.ts:3133–3185`). Repeated visits should not be assessed as separate-scene disposal.
